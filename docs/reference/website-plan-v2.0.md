# 服装工厂 B2B 独立站方案 v2.0
## 工厂官网 · SEO 获客 · 邮箱与 WhatsApp 直接询盘 · 轻量首期

版本日期：2026-09-07  
文档用途：确定首期范围、页面框架、内容与转化设计，为后续 PRD 提供依据。  
版本关系：本版替代 v1.0 关于对外身份、职责分工、首期页面数量和询盘系统的要求，不与旧版相应 P0 需求叠加。

> 已确认：这是帮助工厂建设和运营的官网。网站以工厂为主体，可以真实使用“我们的工厂”“工厂直供”等身份表达。你们负责网站搭建与运营；工厂直接承接邮件、WhatsApp 询盘及报价、打样、生产等后续业务。
>
> 方案建议：英文单语言；先上线约 10 个页面；不开发站内询盘后台、文件上传、CRM 或订单系统。页面数量、具体栏目和内容节奏是控制工作量的建议，不是搜索引擎的收录或排名门槛。文中 T-shirts、Hoodies 是品类示例，须换成工厂真正擅长的品类。MOQ、交期、认证等数字不作预设。

## 1. 项目定义和职责边界

### 1.1 网站定位

建立一个以 SEO 为主要获客入口的英文服装工厂官网，向海外初创及成长型品牌说明制造能力、小批量定制条件和合作流程，引导客户直接联系工厂业务人员。

网站首先完成三件事：让合适的客户找到工厂；让客户判断工厂是否适合自己的项目；让客户顺利通过邮箱或 WhatsApp 开始沟通。

```text
搜索 / 其他来源
    → 首页、品类页、制造服务页或采购文章
    → 了解能力、MOQ、样品及真实工厂信息
    → 选择 Email 或 WhatsApp
    → 工厂收到客户主动发送的消息
    → 工厂沟通、报价、打样、生产与交付

你们：负责搜索到联系入口这一段，并依据工厂反馈优化网站。
工厂：负责真实对话开始后的业务承接，并回传必要结果。
```

### 1.2 分工

| 工作 | 你们 | 工厂 |
|---|---|---|
| 网站设计、代码、部署和维护 | 主责 | 配合确认品牌与资料 |
| 关键词研究、页面内容、文章、SEO | 主责 | 提供专业资料并审核事实 |
| 图片、品类、MOQ、工艺和交期 | 整理发布 | 提供并确认真实性 |
| 邮箱、WhatsApp 与英文回复 | 配置网站入口、测试跳转 | 提供实际可用账号并负责接待 |
| 报价、打样、收款、生产与售后 | 不纳入网站产品范围 | 主责 |
| 效果评估 | 搜索与网站行为分析 | 反馈真实询盘、合格性及项目进展 |

前期只需明确网站与账号的管理权限、日常接待人和资料确认人，不为此建设一套新的业务管理软件。联系人变更后，网站设置也必须同步更新。

### 1.3 对外表达

可用方向：

> Custom Clothing Manufacturing for Emerging Brands
>
> Work directly with our factory in China to develop and produce your next collection. Explore our garment capabilities, sampling process and minimum order requirements.

这是文案方向，不是固定终稿。首页使用工厂品牌、车间与样品，Our Factory 介绍真实厂址、团队和制造能力，不再以撮合平台或供应链中间服务商为主叙事。

“有自有工厂”与“所有工序都由厂内完成”是不同陈述；如存在外协工序，具体能力说明仍按真实安排写。不要使用未经工厂确认的产能、认证、客户标识和响应时限。

## 2. 首期页面：8 个固定页面 + 2 篇文章

### 2.1 明确的上线范围

| 页面 | 建议路径 | 主要用途 |
|---|---|---|
| 首页 | `/` | 工厂定位、核心品类、优势和联系入口 |
| 定制制造服务 | `/manufacturing/` | 合并介绍定制方式、MOQ、打样、流程和采购 FAQ |
| 核心品类 A | `/clothing/t-shirts/` | 该品类的制造能力、样品、条件和询盘入口 |
| 核心品类 B | `/clothing/hoodies/` | 同一品类模板，填入有实际差异的内容 |
| 我们的工厂 | `/our-factory/` | 真实车间、团队、质检和可公开资质 |
| 博客列表 | `/blog/` | 展示采购知识文章 |
| 联系工厂 | `/contact/` | 邮箱、WhatsApp、工作时段和需求准备提示 |
| 隐私说明 | `/privacy/` | 按实际使用的数据与第三方工具说明处理方式 |
| 文章 1 | `/blog/what-to-send-for-a-clothing-quote/` | 询价时应准备什么资料 |
| 文章 2 | `/blog/moq-per-style-per-color/` | MOQ 按款、按色、混尺码如何理解 |

合计 10 个内容 URL。404、sitemap、robots.txt 等属于工程配置，不计入营销页面数量。网站使用条款、Cookie 说明等按实际业务与工具配置评估是否补充，不以本表代替具体政策复核。

两篇文章复用一个详情模板，两个品类复用一个品类模板；不是分别开发十套页面系统。

若工厂有第三个特别有优势且资料完备的品类，可以后续增加，不因“目录看起来不够满”而扩展。

### 2.2 导航

```text
[工厂 Logo]   Clothing   Manufacturing   Our Factory   Blog   [Contact Us]
```

Clothing 首期直接下拉链接到两个品类，不强制开发单独的 `/clothing/` 汇总页。品牌 Logo 返回首页。Privacy 放在页脚，不占主导航。

没有 `/clothing/` 页面时，面包屑不要链接到不存在的父级；可以直接显示 Home → Hoodies。文章使用 Home → Blog → 文章。

### 2.3 原本分散的页面先合并

| 内容 | 首期安置位置 | 何时再独立 |
|---|---|---|
| Low MOQ、Small Batch | Manufacturing 的明确区块 | 有独立搜索意图、足够资料且现页难以承接时 |
| Private Label、Cut & Sew | Manufacturing 中说明真实提供的方式 | 确实有差异化服务与采购需求时 |
| Sampling | Manufacturing 中打样区块 | 有完整费用、改样和开发资料可展开时 |
| Quality Control | Our Factory 的质检区块，品类页补相关细节 | 有独立记录、流程和采购价值时 |
| Fabrics / Customization | 对应品类页 | 有足够材料或工艺资料时 |
| 客户案例 | 工厂页或品类页中的获授权示例 | 有真实完整案例可持续发布时 |
| FAQ | 放在相关页面 | 首期不另做一个空泛 FAQ 页面 |
| 单个样品详情 | 嵌入品类页 | 样品有独立规格与采购价值时 |

合并的是页面入口，不是删除必要信息。客户仍应在首期了解如何定制、起订条件、打样步骤和如何联系。

## 3. 核心页面内容规格

### 3.1 首页

建议采用六个主要模块：定位与双联系按钮；两个核心品类入口；工厂真实优势与证据；定制/MOQ/打样摘要；工厂图片和简要流程；常见问题与联系入口。

首页不承担解释所有工艺的任务，也不把全文扩展成关键词列表。首页负责概览，细节交给制造服务页和品类页。

首屏主次按钮可采用 `Chat on WhatsApp` 与 `Email Our Factory`。没有实际服务能力验证，不宣传“最低价”“立即精确报价”“全天在线”或具体小时内回复。

### 3.2 品类页

| 模块 | 必要内容 |
|---|---|
| 标题与介绍 | 明确这是为品牌提供制造服务，不是零售成衣 |
| 实物样品 | 少量真实成衣与细节图，建议初期 4–6 组，不是必须配额 |
| 能力参数 | 该品类实际可做的面料、版型、尺寸与印绣花等 |
| MOQ 与打样 | 写清计量方式、条件、需要工厂进一步确认的项目 |
| 工厂证据 | 与该品类相关的生产、检查或开发照片 |
| 常见问题 | 3–5 个真实采购问题，按资料量决定 |
| 双联系入口 | Email 与 WhatsApp，并带入品类名称/公开样品编号 |

首期样品是展示能力的内容块，不建颜色、尺码、库存、促销和购物车系统。没有足够独立说明的样品，不单独生成商品 URL。

页面间不能只换 T-shirt / Hoodie 名字而保留完全相同的正文。该品类有什么独特能力，就重点解释什么；没有的能力不硬凑。

### 3.3 Manufacturing

用一个页面回答客户最常见的采购问题，建议区块：

```text
我们提供的定制方式
→ 起订条件与数量算法
→ 客户准备哪些资料
→ 打样与修改流程
→ 样品确认后如何进入量产
→ 常见问题
→ Email / WhatsApp
```

MOQ 必须说明按款还是按色、能否混码、面料和辅料是否有额外限制。能加标与能从零开发不是同一项能力；只有工厂实际提供时才分别介绍。

具体 MOQ、费用和交期由工厂给定。尚未确认的数据不填示例值，使用真实的条件说明或明确说明需根据项目评估。

### 3.4 Our Factory

以真实工厂介绍、车间和工艺照片、团队或部门、质检方式及经过确认的资质为核心。缺少客户公开授权时不设品牌 Logo 墙；没有视频时不为填位置制作虚假的“生产实拍”。

照片说明应让客户看懂拍的是什么工序，而不只写“高品质生产”。质量控制首期放这里，暂不独立成页。

### 3.5 Contact

联系页不等于询盘表单。首期内容为：工厂真实邮箱、WhatsApp、联系人/部门、工作时段、地址，以及一段简短的需求准备提示。

建议提示客户提供品类、预计数量、交付国家，以及有的话提供设计或参考图。不要求每个客户都有 Tech Pack，也不要求先填完资料才允许联系。

联系入口应遍布关键页面，不强制客户绕到 Contact 页面再点击。Contact 是完整联系方式和备用路径的汇总页。

### 3.6 文章

首批两篇分别解决“如何准备询价资料”和“怎样理解 MOQ”。前者引导到制造服务与联系入口，后者解释通用概念并链接到工厂的实际 MOQ 条件，避免与 Manufacturing 大段重复。

文章模板包括标题、摘要、正文、真实署名或工厂团队署名、真实发布日期/更新日期、相关品类/服务和联系入口。作者资料可以先用简单字段，不开发复杂作者中心。

## 4. 首期询盘：直接转向工厂，不在网站接单

### 4.1 WhatsApp 入口

使用 WhatsApp 官方 Click to Chat 链接；这项链接功能无需先开发 WhatsApp Business API 集成。号码使用完整国际格式，链接中不带 `+`、括号或分隔符，不随意删除号码内部的零。[S01]

格式说明：

```text
https://wa.me/<国际格式号码，仅数字>?text=<经过 URL 编码的短消息>
```

品类页的预填消息建议简短：

```text
Hi, I found your hoodie manufacturing page on your website.
I'd like to discuss a custom order for my brand.
Reference: WEB-HOODIES
```

公开样品有编号时可加样品编号。预填内容仅包含页面/品类等公开上下文，不自动加入访客身份、完整追踪参数或设计内容。不要预填一大段问卷。

客户仍需主动点击发送；打开聊天不是工厂已经收到询盘。WhatsApp 官方说明预填内容出现在聊天输入框中，因此网站不得在跳转后显示“已成功提交询盘”。[S01]

工厂应在上线测试前提供实际接待账号，并用真实设备验证账号可收发消息。

### 4.2 邮箱入口

采用可见邮箱地址 + `mailto:` 按钮 + 复制邮箱三个方式。`mailto:` 可打开用户的邮件程序，并支持预填主题和正文；它本身不是网站代发邮件的接口。[S02]

主题示例：

```text
[Website][Hoodies] Custom clothing inquiry
```

可选的简短正文示例：

```text
Hello,
I found your hoodie manufacturing page and would like to discuss a project.

Product:
Estimated quantity:
Delivery country:
Reference: WEB-HOODIES
```

客户在邮件客户端自行补充资料和添加附件。网站不声称已上传文件、已发送邮件或工厂已读。不要试图通过普通 mailto 链接自动附加客户本地文件。

用户设备未配置合适邮件处理程序时，保留复制和手动选择邮箱地址的路径。复制操作失败时提示“请手动复制”，不要显示虚假的成功提示。

工厂有条件时，可提供仅用于该网站的邮箱或邮箱别名，便于识别网站来源；这不是网站开发的硬性前提。

### 4.3 展示位置

桌面端：首屏、品类与服务说明结束处、页脚提供明显的两个联系方式。移动端可使用简洁的底部双按钮，不遮挡正文、页脚或必要的隐私设置。

链接采用真实 `<a href>`，分析脚本失效也应能跳转；复制才使用按钮和少量脚本。首期不接重型聊天弹窗、AI 接待或扫码才能联系的流程。[S02]

### 4.4 首期不开发的能力

不开发站内提交接口、客户附件上传、询盘数据库、通知队列、事务邮件 API、自动回执、CRM 工作台、聊天消息同步、自动报价、订单管理和在线支付。

工厂通过既有邮箱与 WhatsApp 处理客户资料。客户设计稿不进入网站公开 CMS。放弃站内收单意味着网站不能独立证明客户是否发出消息，这一取舍由轻量范围决定，不通过虚构成功事件掩盖。

## 5. 技术方案：Astro + Sanity，公开页面静态生成

### 5.1 技术边界

| 部分 | 首期实现 |
|---|---|
| 前端 | Astro + TypeScript，响应式页面，少量交互 |
| 内容 | Sanity 管理公开文案、品类、样品图片、文章与联系方式 |
| 页面输出 | 默认静态生成，公开内容在构建时生成 HTML |
| 托管 | 支持 Astro 静态产物、HTTPS、重定向和构建流程的平台 |
| 联系 | mailto 与 WhatsApp 官方直达链接 |
| SEO | 统一元数据、规范 URL、sitemap、robots 与结构化内容 |
| 数据 | Search Console；按已确认配置启用必要点击事件 |
| 后端业务系统 | 无自建询盘数据库、上传存储和 CRM |

Astro 默认支持静态输出，官方也列出 Sanity 的集成入口。本项目不需要为每次访问运行询盘后端，因为首期网站没有站内提交能力。[S03][S04]

Astro 本身不保证排名；技术底座之外，工厂资料、内容、搜索意图和持续运营仍是项目工作。

### 5.2 发布流程

```text
你们在 Sanity 编辑并发布公开内容
    → 触发网站构建
    → 构建时读取已发布内容
    → 发布静态网站
    → 访客访问并选择联系方式
```

静态站需要重建才能反映内容更新，可通过 Sanity Webhook 触发托管平台构建。构建时读取最新已发布内容，首期可按官方静态方案使用 `useCdn: false`；具体集成按选定版本验证。[S05]

需验收发布、修改、撤回/删除都会反映到正式站；构建失败不覆盖当前正常网站。Webhook 或构建入口应受平台提供的密钥、签名或相应机制保护，不公开在前端。首期不做高级可视化编辑、任意拖拽页面构建器或公开草稿预览。

### 5.3 最少的 CMS 内容模型

| 类型 | 关键字段 |
|---|---|
| `siteSettings` | 工厂品牌、Logo、邮箱、WhatsApp 国际号码、地址、工作时段、全局导航 |
| `page` | 首页/制造服务/工厂/联系/政策的固定模块内容，SEO 字段 |
| `category` | 名称、slug、简介、实际能力、样品图库、该品类 MOQ 与打样说明、FAQ、SEO |
| `article` | 标题、slug、摘要、正文、封面、署名、日期、关联品类和服务、SEO |

SEO 作为共享对象，包含 title、description、分享图等。规范链接通常由正式域名和路径生成，不向普通编辑者暴露容易误填的覆盖选项。样品作为品类中的数组，不先建立 SKU 系统。

联系方式只维护一处，全站读取同一配置。MOQ 可以按品类不同，但应有工厂确认记录；不要在各处手工写互相矛盾的起订数字。

### 5.4 必须保留的工程质量

代码版本管理；生产域名和正式配置；HTTPS；真实 404；手机与桌面测试；图片压缩与尺寸声明；不依赖大体积视频；CMS 访问控制；密钥不暴露给浏览器；公开内容备份与部署回滚；构建结果可检查。

“轻量”意味着少做业务功能，不意味着把链接、发布和基础 SEO 做成不可维护的临时方案。

## 6. SEO：基础先完成，内容逐步增加

### 6.1 第一版的内容分工

| 页面 | 建议承接的主要意图 | 备注 |
|---|---|---|
| 首页 | 中国服装工厂、品牌服装定制的整体需求 | 工厂身份与概览，不重复展开所有服务 |
| Manufacturing | 小批量制造、起订条件、定制与打样流程 | 首期合并承接，不保证覆盖所有服务词 |
| 两个品类页 | 寻找对应服装品类的制造商 | 比单纯图片目录更完整地回答采购问题 |
| Our Factory | 验证工厂身份与生产能力 | 优先为信任与决策服务 |
| 两篇采购文章 | 准备项目资料、理解起订规则 | 帮助客户继续进入服务或品类页 |

英文关键词可以从 `custom clothing manufacturer China`、`low MOQ clothing manufacturer` 和真实品类相关查询开始研究，但这些只是候选，不含已验证的搜索量、竞争难度或流量预测。

不要把每个相近词都变成一页。首期保留清楚的页面分工，后期依据目标市场搜索结果、Search Console 和工厂实际能力决定是否拆页。

### 6.2 上线前完成的 SEO 基础

公开核心内容可直接在 HTML 中读取；标题与描述围绕各页实际内容；路径稳定且含义清楚；导航、面包屑和正文链接可访问；图片有合理文件信息与描述性替代文本。Google 的入门指南强调可抓取、可理解的结构和对用户有帮助的内容，而非固定页面数量。[S06]

正式主域名、站内链接、canonical 和 sitemap 保持一致。sitemap 只列计划索引的正式规范页面，并随新增/撤回内容更新；提交 sitemap 不是收录保证。[S08][S12]

测试站、草稿和管理界面不能意外公开；需要隔离的预览先控制访问。robots.txt 禁止抓取不等于禁止收录；需要 Google 识别 noindex 时，不能同时阻止它抓取该页。[S09]

结构化数据仅按真实内容添加，如组织、面包屑、文章；不虚构产品价格、库存、评价或承诺特定富结果。首期不把所谓特殊 SEO 插件当作上线条件。

### 6.3 内容节奏

先完成商业页面，再准备两篇可发布文章。上线后可以按团队能力，每 1–2 周完成一篇有工厂资料支撑的内容，同时更新已有商业页；这只是工作节奏建议，不是必须频率，也不是 SEO 见效承诺。

文章题材来自真实询盘和工厂解释，例如面料克重、印绣花选择、打样需要什么、不同颜色为什么影响起订量。每篇只链接到实际相关的服务/品类，并提供自然的联系入口。

Google 明确建议提供原创、有帮助、以用户为先的内容；不会因为为搜索引擎凑固定字数或频繁换日期就自动获得优势。AI 可以辅助语言整理，但工厂规则、案例与照片必须来自实际资料。[S07]

### 6.4 何时增加页面

新增页应能回答现有页面没有充分回答的独立采购问题，并且有工厂能力和素材支持。可以使用以下判断：相关搜索需求或询盘问题反复出现；有足够独立内容；新页有明确负责的意图；有人能维护。

例如，多次收到特定针织卫衣的询盘，而且工厂有稳定样品与相关能力，可以优先补充该主题，而不是先做大量无实际资料的国家页或颜色页。

拆页时保留原 Manufacturing 页的摘要与相关链接，不把原文整段复制到新页；已公开 URL 变动时处理重定向。这个 10 页范围是起点，不是长期不扩展的限制。

## 7. 效果统计：点击、真实询盘、有效机会分开

### 7.1 网站知道什么

网站侧可以统计搜索展示与点击、落地页表现，以及 `contact_whatsapp_click`、`contact_email_click`、`contact_email_copy` 等联系行为。

建议事件参数仅保留 page_type、公开品类标识、button_position、contact_channel 等必要信息。不要把完整 WhatsApp/mailto 链接、号码、邮箱、消息正文或客户设计内容发给分析服务。Google Analytics 对发送可识别个人信息有明确限制。[S10]

如启用 GA4，需检查并适当关闭或调整自动出站链接采集，避免其默认采集的 link_url 将联系方式和预填消息一起带入；对这两个渠道使用经验证的最小化事件方案。[S11]

分析工具、同意管理及相应政策应按实际配置确认；没有完成配置时先使用 Search Console，并保持事件上报关闭，不能把“已预留代码”报告为“已获得点击数据”。追踪不可用时，正常联系功能仍须可用。

### 7.2 工厂知道什么

```text
点击 WhatsApp ≠ 客户发出消息
点击 Email ≠ 客户发送邮件
复制邮箱 ≠ 真实询盘
真实询盘 ≠ 合格项目
```

这些是本项目的数据边界。直接链接无法让网站自动判断客户是否最终发送消息，也不能自动得到后续报价、打样或订单结果。

### 7.3 最小反馈机制

不开发 CRM。工厂可用现有台账，定期提供下列最少信息：

| 字段 | 用途 |
|---|---|
| 收到日期与渠道 | 区分邮箱/WhatsApp |
| 是否来自本站 | 邮箱别名、预填消息或客户自述；不明就记未知 |
| 品类与大致数量 | 判断网站吸引的项目类型 |
| 是否可承接 | 判断询盘质量 |
| 未继续原因 | 例如 MOQ、价格、品类或时间不匹配 |
| 是否进入报价/打样 | 判断是否产生实际业务机会 |

你们不需要为了运营复盘获取客户全部设计稿或聊天记录。可以由工厂回传去标识汇总，具体数据共享权限由双方确认。

网站点击数用来优化入口；工厂确认的真实、合格询盘用来衡量获客。不能把单次点击统计直接当作询盘 KPI。来源不确定时不要强行归因到 Google 或某个关键词。

## 8. 迭代顺序：按证据增加，不提前铺系统

| 阶段 | 交付内容 | 完成/进入下一步的依据 |
|---|---|---|
| 首期上线 | 10 个内容页、双渠道联系、CMS、SEO 基础 | 信息真实、页面可用、工厂能实际收到测试消息 |
| 上线后持续改进 | 检查搜索与联系入口；调整内容和 MOQ 解释；持续补文章 | 定位真实问题，而非只追求 URL 数量 |
| 扩展有效主题 | 新品类、独立 MOQ/打样/工艺页、真实案例 | 独立搜索意图、真实资料、维护能力具备 |
| 转化能力升级 | 可选简短表单、资料下载或询价辅助 | 确有用户联系困难、资料缺失或管理瓶颈 |
| 更后期 | 多语言、客户门户等 | 明确市场需求、业务价值和维护资源 |

后续表单可以把询盘交给工厂处理，但启用站内收单时需要重新定义可靠保存、通知失败和隐私要求，不能把旧版复杂系统默认为本期隐藏任务。

不设“上线若干天一定有排名/订单”的验收承诺。上线前验收功能与内容，上线后才根据真实搜索和业务反馈判断效果。

## 9. 可直接进入 PRD 的首期需求

以下 P0 仅对应本版范围，不包含 v1.0 的询盘数据库、附件存储与 CRM。

| ID | 需求 | 验收标准 |
|---|---|---|
| SCOPE-01 | 工厂官网定位与内容确认 | 工厂品牌和身份一致；所有经营数字由工厂确认 |
| PAGE-01 | 首期页面与导航 | 8 个固定页 + 2 篇文章可访问，无空栏目和死链接 |
| PAGE-02 | 品类模板 | 两个品类复用模板，但图片与能力说明有实际区别 |
| CONTACT-01 | WhatsApp 直达 | 号码正确；手机与桌面可到达可用接待入口；预填内容可编辑；不自动宣称已收询盘 |
| CONTACT-02 | Email 与复制 | 地址可见；mailto 主题正确；复制失败可手动选择；不宣称已发邮件 |
| CONTACT-03 | 上下文与统一设置 | 品类/样品引用正确；修改工厂联系方式后全站部署更新 |
| CMS-01 | 可编辑公开内容 | 运营可修改页面、品类和文章，不为普通内容变更修改代码 |
| CMS-02 | 发布与撤回 | 只取已发布内容；修改、撤回可进入部署；失败保留原站并可发现 |
| SEO-01 | 页面元数据与规范地址 | title/description 合理；canonical、内链、sitemap 一致 |
| SEO-02 | 搜索访问与环境隔离 | 正式内容可抓取；无误设全站 noindex；草稿和管理入口受控 |
| UX-01 | 手机、桌面与降级 | 联系按钮不遮挡内容；键盘可操作；分析脚本失败不影响联系 |
| DATA-01 | 联系行为指标 | 启用时每次操作按规则记一次；不把点击命名为真实询盘；无敏感链接泄露 |
| OPS-01 | 工厂接待验证 | 从真实设备主动发送测试邮件和消息，工厂确认收到且有人回复 |
| OPS-02 | 内容与业务反馈 | 工厂确认资料的负责人、接待负责人及定期反馈方式明确 |
| MAINT-01 | 维护与恢复 | 代码与内容可备份；部署能回滚；账号权限和域名管理责任明确 |

### 上线阻断项

联系方式错配或无人接待；假数据/未授权资料对外展示；核心页无法访问；跳转链接不可用且无备用路径；草稿泄露；全站意外 noindex；正式 canonical 指向测试站；分析工具采集敏感链接；没有可执行的发布和恢复方法。

SEO 排名、订单数和点击增长不作为“网站功能是否交付”的即时验收条件，另作为持续运营指标观察。

## 10. 开发前由工厂提供的最小资料包

| 资料 | 首期最低要求 |
|---|---|
| 品牌与主体 | 英文名称、Logo、工厂介绍、对外地址和联系人 |
| 核心品类 | 两个真实优势品类、可做/不可做的范围 |
| 商业条件 | 该品类 MOQ 算法、打样方式、可公开的时间与条件说明 |
| 真实图片 | 样品与细节、车间或团队、检查过程；允许公开使用 |
| 接待渠道 | 实际工作的工厂邮箱和 WhatsApp、接待人、工作时段 |
| 内容审核 | 一名能够确认工艺、MOQ 和流程的工厂负责人 |

没有必要为了首期网站让你们学习并承担全部外贸业务。你们需要理解的是客户如何寻找工厂、怎样判断适配、最常问什么，以及网站如何准确呈现工厂提供的答案。

## 11. 最终范围摘要

**第一版 = 工厂身份官网 + 2 个核心品类 + 1 个合并制造服务页 + 工厂介绍 + 联系页 + 博客及 2 篇采购文章 + 隐私说明 + SEO 基础 + 邮箱/WhatsApp 直达。**

**第一版不含 = 表单收单、客户附件上传、询盘数据库、CRM、聊天 API、报价系统、支付和订单管理。**

先把一个小范围、可信、能联系到真实业务人员的网站做好，再依据搜索数据和工厂询盘反馈逐步扩展。这是本版后续 PRD 的边界。
